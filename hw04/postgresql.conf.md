# postgresql.conf

## Путь до конфигурационного файла в Ubuntu
```
/etc/postgresql/*номер версии*/main/postgresql.conf
```
Проверить всегда можно через psql: SHOW config_file; — это универсальный способ, не зависящий от ОС и версии.


## Параметры, которые в реальной практике меняют чаще всего

| Параметр | Что делает / зачем менять | Контекст |
| --- | --- | --- |
| `listen_addresses` | С каких сетевых интерфейсов сервер принимает подключения. 'localhost' — только локально, '*' — все интерфейсы (нужно для доступа снаружи). | postmaster (restart) |
| `port` | TCP-порт сервера. Меняют, если стандартный 5432 занят или запущено несколько кластеров. | postmaster (restart) |
| `max_connections` | Максимум одновременных подключений. Увеличивать осторожно: каждое соединение — отдельный процесс и своя память. В проде часто снижают и ставят PgBouncer. | postmaster (restart) |
| `shared_buffers` | Объём разделяемой памяти под кеш страниц данных. Базовый параметр производительности. Обычно 25–40% ОЗУ. | postmaster (restart) |
| `effective_cache_size` | Ориентир для планировщика: сколько ОС может держать в файловом кеше. Не выделяет память, только влияет на оценку стоимости планов. Обычно 50–75% ОЗУ. | sighup (reload) |
| `work_mem` | Память на одну операцию сортировки/хеширования в запросе. Не на соединение! Завышение → риск OOM при многих одновременных сортировках. | user (можно менять в сессии) |
| `maintenance_work_mem` | Память для VACUUM, REINDEX, CREATE INDEX. Обычно 512 МБ–2 ГБ. | user |
| `wal_level` | Уровень детализации WAL. replica (по умолчанию) — для репликации; logical — если нужна логическая репликация. | postmaster (restart) |
| `fsync` | Принудительная запись WAL на диск. Всегда on в проде; выключают только для ускорения тестов/восстановления. | sighup (reload) |
| `synchronous_commit` | Ждать ли подтверждения записи WAL перед завершением транзакции. off — быстрее, но риск потери последних транзакций при сбое. | user |
| `checkpoint_completion_target` | Насколько «размазать» запись checkpoint по времени. Ближе к 1.0 → меньше пиков I/O. | sighup (reload) |
| `random_page_cost` | Стоимость случайного чтения относительно последовательного. Для SSD ставят ~1.1–1.25, для HDD — выше. | user |
| `max_worker_processes` | Максимум фоновых процессов. Обычно ≤ числа ядер CPU. | postmaster (restart) |
| `max_parallel_workers` | Максимум параллельных воркеров для запросов. Обычно ≤ числа ядер. | sighup (reload) |
| `max_parallel_workers_per_gather` | Сколько воркеров может использовать один узел плана (обычно max_parallel_workers / 2). | user |
| `track_activity_query_size` | Сколько символов текста запроса хранить в pg_stat_activity. По умолчанию 1024 — часто мало для длинных запросов. | postmaster (restart) |
| `log_min_duration_statement` | Логировать запросы дольше N мс. 0 — логировать всё (для отладки), -1 — не логировать. | sighup (reload) |
| `logging_collector` | Включить сбор логов в файлы (иначе идут в stderr/journal). | postmaster (restart) |
| `timezone` | Часовой пояс сервера. Влияет на now(), timestamp with time zone и логи. | user |

Колонка контекст определяет, что делать после правки файла:
- postmaster → restart;
- sighup → reload;
- user → можно менять в текущей сессии через SET, не трогая файл.

Важные уточнения по некоторым параметрам:

1) **listen_addresses: адреса сервера, а не клиента**

Здесь кроется очень важное различие, которое часто путают.

listen_addresses не указывает, каким клиентам можно подключаться. Этот параметр говорит PostgreSQL, на каких сетевых интерфейсах (IP-адресах) самого сервера "слушать" входящие соединения.

- listen_addresses = 'localhost' означает: "принимай соединения только на адрес 127.0.0.1". Клиенты с других машин до тебя физически не достучатся.

- listen_addresses = '*' означает: "принимай соединения на все IP-адреса, которые есть у этой машины" (например, 10.0.2.15 в твоей ВМ).

А вот кто именно может подключаться и с каких IP-адресов — это уже решает pg_hba.conf. Именно там ты указываешь диапазоны адресов клиентов (CIDR), например 10.0.2.0/24 или 192.168.1.0/24.

**Про динамические IP клиентов:**

listen_addresses эту проблему не решает, потому что он про адреса сервера. Решение для клиентов с меняющимися IP-адресами — в pg_hba.conf:

- Указать подсеть (CIDR), а не конкретный IP. Если у клиентов адреса из диапазона 10.1.0.0/16 (даже если они меняются), правило host all all 10.1.0.0/16 scram-sha-256 будет работать для любого адреса из этой сети.

- Использовать другие механизмы аутентификации, не завязанные на IP, например, сертификаты (cert) или аутентификацию через внешние сервисы (LDAP, PAM). Но это уже выходит за рамки базовой настройки.

Так что запомни цепочку: listen_addresses (на каких адресах сервера слушать) → pg_hba.conf (с каких адресов клиентов пускать) → аутентификация (как проверять пользователя).

2) **max_connections: что такое "подключение" и как всё сломать**

Что считается подключением?

В PostgreSQL каждое клиентское подключение — это отдельный серверный процесс (backend). max_connections — это жесткий лимит на количество таких процессов, которые могут одновременно существовать.

- Каждая новая вкладка в pgAdmin (или любом другом GUI-клиенте) обычно открывает своё собственное подключение. Если у тебя открыто несколько вкладок, каждая из них "съедает" один слот из max_connections.

- Каждый экземпляр приложения (например, каждый поток или процесс на бэкенде), который устанавливает соединение с БД, тоже занимает слот.

- Важно: один и тот же пользователь (usename) может иметь много подключений. Лимит считается по общему числу подключений, а не по числу уникальных пользователей.

Проверить, сколько слотов занято прямо сейчас, можно так (это покажет только клиентские подключения):

```sql
SELECT count(*) FROM pg_stat_activity WHERE backend_type = 'client backend';
```

**Что будет, если занять все 100 слотов?**

Когда лимит достигнут, любая новая попытка подключения будет отвергнута с фатальной ошибкой:
FATAL: sorry, too many clients already.

Самые простые способы "положить" сервер по подключениям:

- "Вилка" через GUI-клиент: Открыть много вкладок в pgAdmin (или другом клиенте), каждая из которых держит соединение. Это самый простой и наглядный способ в учебной среде.

- Утечка соединений в приложении: Приложение открывает соединения и не закрывает их (например, из-за ошибки в коде). Постепенно все слоты оказываются занятыми "простаивающими" (idle) или "простаивающими в транзакции" (idle in transaction) процессами.

- "Thundering herd" (стадо): После перезапуска приложения или сервера все его экземпляры одновременно пытаются установить соединение, мгновенно исчерпывая лимит.

Важный нюанс: несколько слотов зарезервировано для суперпользователей (по умолчанию superuser_reserved_connections = 3), чтобы администратор мог зайти и починить ситуацию, даже если все "обычные" слоты заняты.

Важно: Увеличение max_connections — это часто неправильное решение. Каждое подключение — это процесс, который потребляет память и ресурсы планировщика ОС. Если соединений слишком много, сервер начнет "тормозить" из-за переключений контекста и нехватки памяти, а не работать быстрее. Правильный путь — использовать пул соединений (PgBouncer), но это, как ты и сказал, тема для отдельного разговора.

3) **shared_buffers: кеш данных в памяти PostgreSQL**

Представь, что данные на диске — это огромная библиотека, а shared_buffers — это небольшой, но очень быстрый стеллаж прямо в комнате, где ты работаешь.

shared_buffers — это область разделяемой памяти, которую PostgreSQL использует как кеш для страниц данных (блоков), прочитанных с диска.

Как это работает:

- Когда ты выполняешь запрос, PostgreSQL сначала ищет нужные данные (страницы по 8 КБ) в shared_buffers.

- Если данные есть в памяти (кеш-попадание) — сервер читает их оттуда. Это очень быстро.

- Если данных нет (кеш-промах) — сервер читает их с диска и помещает в shared_buffers, чтобы при следующем обращении к ним не идти на диск снова.

Ключевые моменты для понимания:

- Это не "память для сортировки" и не "память для соединения". Это именно кеш данных, общий для всех процессов сервера. Он выделяется один раз при старте сервера и не освобождается между запросами.

- Это не единственный кеш. Операционная система тоже кеширует файлы на диске (page cache). PostgreSQL "сотрудничает" с ОС: он кеширует у себя, а ОС кеширует то, что не влезло в shared_buffers. Поэтому параметр effective_cache_size (оценка суммарного кеша ОС + PostgreSQL) так важен для планировщика.

- Сколько выделять? Классическая рекомендация — 25–40% от общей оперативной памяти сервера. Слишком маленький shared_buffers приведет к частым чтениям с диска, слишком большой — может "зажать" память, необходимую ОС и другим процессам.

shared_buffers — это фундаментальный параметр, который напрямую влияет на то, насколько быстро база данных будет отдавать уже "прогретые" (часто используемые) данные.


## Если говорить о том, что чаще всего настраивают в первую очередь для продакшена, то это:

shared_buffers, work_mem, effective_cache_size, max_connections, maintenance_work_mem. Это базовые параметры памяти и подключений, которые дают наибольший эффект при правильной настройке.

К параметрам, которые часто желательно менять от «заводских» настроек, относятся:

- shared_buffers — с 128MB до 25-40% ОЗУ.

- work_mem — с 4MB до значения, адекватного нагрузке (часто 16-64MB).

- effective_cache_size — установить в 50-75% ОЗУ.

- max_connections — уменьшить и использовать пул соединений.

- checkpoint_completion_target — установить в 0.9 для сглаживания пиков ввода-вывода.

- random_page_cost — понизить для SSD (например, до 1.1-1.25).

## Правильный listen_addresses для продакшена

Самый правильный подход — никогда не использовать '*'. Нужно указывать конкретные IP-адреса интерфейсов сервера, на которых он должен принимать подключения.

На практике это означает:

- Если база данных общается с приложением по приватной сети, укажи IP-адрес сервера в этой сети: listen_addresses = '10.0.0.5'.

- Если нужен доступ и с локальной машины, и из сети: listen_addresses = 'localhost,10.0.0.5'.

- 'localhost' оставляй только для локальной разработки или если сервер вообще не должен быть доступен по сети.

Это ограничивает поверхность атаки и предотвращает случайные подключения с нежелательных интерфейсов.

## Защита от «диверсий» в pgAdmin

Можно и нужно ограничивать подключения на уровне ролей. Для этого существует параметр CONNECTION LIMIT.

- Как включить: Выполни команду ALTER ROLE имя_роли CONNECTION LIMIT количество;.

- Как это работает: Это жесткий лимит на количество одновременных подключений для конкретной роли. Если бизнес-аналитики используют общую учетную запись, лимит для этой роли будет общим для всех них.

- Снять лимит: ALTER ROLE имя_роли CONNECTION LIMIT -1; (значение -1 означает «без ограничений»).

- Лимит на базу данных: Аналогично можно ограничить количество подключений к конкретной базе: ALTER DATABASE имя_базы CONNECTION LIMIT количество;.

Что касается алертов: Мониторинг pg_stat_activity и настройка оповещений при приближении к лимиту max_connections (например, на 70-80%) — это стандартная практика. Также очень полезно настроить параметры idle_session_timeout и idle_in_transaction_session_timeout, которые будут автоматически закрывать «простаивающие» соединения, чтобы они не занимали слоты.

## Сколько данные лежат в shared_buffers?

Данные (страницы) находятся в shared_buffers до тех пор, пока их не вытеснят оттуда новые данные. PostgreSQL не использует простой алгоритм LRU («давно не использованные вытесняются первыми»).

Вместо этого используется алгоритм clock-sweep (разновидность «часового» алгоритма). Упрощенно это работает так:

- У каждой страницы в кеше есть счетчик «полезности» (от 0 до 5).

- При каждом обращении к странице счетчик увеличивается (но не более 5).

- Когда нужно освободить место для новой страницы, «часовая стрелка» проходит по страницам и уменьшает их счетчики. Страница с нулевым счетчиком считается «холодной» и вытесняется.

Таким образом, «горячие» данные (к которым часто обращаются) остаются в памяти очень долго, а «холодные» — вытесняются при первой необходимости. Время жизни данных в кеше не фиксировано и зависит исключительно от интенсивности их использования и общего объема shared_buffers.

# postgresql.auto.conf и как правильно править конфигурацию

Правки в postgresql.conf можно вносить напрямую, но это не самый предпочтительный способ потому, что он никак не валидируется и если в файле будет неверный синтаксис - сразу это может быть не обнаружено. Синтаксическая ошибка (опечатка в имени параметра, неверная единица измерения, пропущенная кавычка) не будет видна до момента применения, и может привести к ошибке:
- При reload сервер не упадёт. Он запишет в лог сообщение вида configuration file "..." contains errors; unaffected changes were applied и продолжит работать со старыми значениями. То есть ты узнаешь об ошибке только по логам.
- При restart ошибка в конфиге может помешать серверу запуститься.

Если же всё-таки выбрать путь редактирования конфигурации через postgresql.conf, нужно соблюдать правило - не править параметры, которые уже есть в файле, а вести отдельную секцию в самом низу файла, переоделяя значения там, оставляя исходные наверху, там, где они и были. Так как postgresql.conf читается сверху вниз, то значения находящиеся ниже переопределят более ранние (если параметр встречается несколько раз, действует последнее значение). И ещё это нужно для удобства, чтобы все переопределенные от дефолта параметра были в одном месте, а также помнить дефолтное значение.

Но самый правильный способ редактирования конфигурации - через postgresql.auto.conf.

## postgresql.auto.conf

Он лежит в каталоге данных (data directory), а не в /etc/postgresql/... Наиболее вероятное место расположения файла: `/var/lib/postgresql/*номер версии*/main/postgresql.auto.conf`. Этот файл имеет тот же формат, что и postgresql.conf, но предназначен для автоматического редактирования, а не для ручной правки. Физически "руками" postgresql.auto.conf править тоже можно, но так делать не нужно - он предназначен для редактирования через `ALTER SYSTEM`.

Команды ALTER SYSTEM выполняются как обычный SQL-запрос — через psql, pgAdmin или любое другое клиентское приложение, под пользователем с правами суперпользователя (или специальной привилегией).

Значения из postgresql.auto.conf имеют более высокий приоритет. postgresql.auto.conf читается после postgresql.conf и переопределяет значения из него. Если параметр задан в обоих файлах, победит значение из auto.conf.

Примеры команд (выполняются в psql):
```sql
-- Задать параметр
ALTER SYSTEM SET work_mem = '64MB';

-- Сбросить параметр (вернуть значение из postgresql.conf или по умолчанию)
ALTER SYSTEM RESET work_mem;
```

Удалить запись оттуда можно только двумя способами:

- ALTER SYSTEM RESET имя_параметра; — сбросить конкретный параметр.

- ALTER SYSTEM SET имя_параметра = DEFAULT; — то же самое, что и RESET.

Обе команды удаляют соответствующую строку из postgresql.auto.conf, после чего снова начинает действовать значение из postgresql.conf (или значение по умолчанию).

Таким образом, 

### Важные нюансы:

- ALTER SYSTEM проверяет существование параметра и корректность значения при выполнении команды, что снижает риск синтаксических ошибок. Но это не полная валидация всех возможных проблем.

- Команда не может выполняться внутри транзакции и не может быть отменена (rollback), так как она напрямую меняет файл на диске.

- Как и при ручной правке, изменения вступят в силу после reload (для большинства параметров) или restart (для параметров с контекстом postmaster).

- Файл postgresql.auto.conf создаётся пустым при инициализации кластера (или его может не быть до первого использования). Записи в нём появляются исключительно в результате выполнения команд ALTER SYSTEM SET. Вручную редактировать его не нужно и не рекомендуется — для этого и существует ALTER SYSTEM.

- Записи из postgresql.auto.conf никуда не удаляются при перезагрузке или перечитывании конфигурации. Наоборот, файл читается при каждом старте сервера и имеет приоритет над postgresql.conf. Поэтому если параметр задан в обоих файлах, после любого рестарта продолжит действовать значение из auto.conf/ postgresql.auto.conf — это как «слой переопределений», который создаётся командами ALTER SYSTEM, живёт в каталоге данных, сохраняется между перезапусками и снимается только явным RESET.

### Практический вывод

Для быстрых и безопасных изменений на работающем сервере (особенно если ты не уверен в синтаксисе) — используй ALTER SYSTEM. Это рекомендуемый способ для большинства рутинных правок.

Для полного контроля над конфигурацией, документирования всех настроек в одном месте или если нужно изменить параметр, который нельзя задать через ALTER SYSTEM (например, data_directory), — редактируй postgresql.conf вручную, но обязательно проверяй результат в логах после reload.

### Порядок проверки при расхождениях

Если pg_settings показывает не то, что ты ожидаешь увидеть в postgresql.conf, то postgresql.auto.conf — первый подозреваемый. Он читается после postgresql.conf и переопределяет его.

Но есть ещё пара мест, откуда может «прилететь» неожиданное значение, и о них стоит помнить:

- Переменные окружения (PGOPTIONS, PGPORT и т.п.) и опции командной строки при старте сервера — они тоже могут переопределять конфиг.

- Настройки уровня базы/роли (ALTER DATABASE ... SET, ALTER ROLE ... SET) — действуют только в контексте конкретной базы или пользователя.

- Настройки уровня сессии (SET, SET LOCAL) — действуют только в текущем подключении.

Самый надёжный способ не гадать, а сразу увидеть источник — это колонка source в pg_settings:
```sql
SELECT name, setting, source, sourcefile, sourceline
FROM pg_settings
WHERE name = 'work_mem';
```

Колонка source покажет одно из значений: default, configuration file, environment variable, command line, database, user, client, override и т.д. А sourcefile/sourceline (если применимо) укажут конкретный файл и строку. Это самый быстрый путь к ответу «откуда взялось это значение».

### Ручная правка postgresql.auto.conf (плохая практика)

Физически можно открыть файл редактором и поправить руками — это обычный текстовый файл. Но это не приветствуется, и вот почему:

- Нет валидации. ALTER SYSTEM проверяет имя параметра и корректность значения при выполнении. Ручная правка — нет; ошибку увидишь только в логах после reload/restart.

- Файл предназначен для автоматической генерации. В самом файле обычно есть комментарий-предупреждение, что он управляется командой ALTER SYSTEM и ручные правки могут быть перезаписаны или привести к неожиданностям.

- Формат может быть чувствителен. ALTER SYSTEM пишет значения в каноническом виде (с правильными кавычками, единицами и т.д.). Руками легко нарушить формат.

- Сложнее поддерживать. Если ты правишь файл руками, а потом делаешь ALTER SYSTEM RESET, можно получить неожиданный результат, потому что система ожидает, что файл соответствует её внутреннему представлению.

Ручная правка допустима разве что в аварийной ситуации, когда сервер не стартует и ALTER SYSTEM выполнить нельзя (но тогда лучше править postgresql.conf или использовать postgresql.auto.conf с крайней осторожностью).
