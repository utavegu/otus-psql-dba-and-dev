# Host-Based Authentication
(аутентификация на основе узла/хоста)

Файл pg_hba.conf отвечает за то, кто и откуда имеет право подключаться к серверу PostgreSQL, по какому протоколу и каким способом должен подтверждать свою личность (пароль, сертификат, доверенное соединение и т. д.).

Правила в файле читаются сверху вниз до первого совпадения с параметрами клиента (IP-адрес, имя пользователя, база данных).

Этот файл устроен принципиально иначе, чем postgresql.conf: если postgresql.conf — это «набор параметров», то pg_hba.conf — это упорядоченный список правил доступа. И именно порядок правил здесь является вопросом безопасности, а не стиля.

## Расположение файла

В Ubuntu путь к файлу такой же, как и у postgresql.conf:
```
/etc/postgresql/*номер_версии*/main/pg_hba.conf
```
Проверить актуальный путь всегда можно через psql:
```
SHOW hba_file;
```
Это универсальный способ, не зависящий от ОС и версии. Файл читается при старте и при получении сигнала SIGHUP (то есть при reload).

## Структура

Каждая строка — это правило из нескольких полей, разделённых пробелами или табами. Типичный формат:
```
ТИП_ПОДКЛЮЧЕНИЯ  БАЗА  ПОЛЬЗОВАТЕЛЬ  АДРЕС  МЕТОД_АУТЕНТИФИКАЦИИ  [опции]
```

Ключевой принцип: PostgreSQL читает файл сверху вниз и останавливается на первом правиле, которое совпало по типу подключения, адресу, базе и пользователю. Если аутентификация по этому правилу провалилась, следующие правила не проверяются — соединение отклоняется. Если ни одно правило не совпало — доступ запрещён.

Это означает, что узкие, специфичные правила должны идти выше, а широкие — ниже. Если поставить широкое правило (0.0.0.0/0) выше узкого, то узкое правило уже никогда не сработает.

## Основные типы подключений

| Тип | Что означает
| --- | --- |
| `local` | Подключение через Unix-сокет (локально на сервере) |
| `host` | TCP/IP-подключение (с SSL или без) |
| `hostssl` | TCP/IP только с SSL |
| `hostnossl` | TCP/IP только без SSL |

Для продакшена часто используют hostssl для всех сетевых подключений, чтобы трафик (включая пароли и данные) не шёл в открытом виде.

## Методы аутентификации, которые важно знать

- `peer` — сопоставляет имя пользователя ОС с именем роли в PostgreSQL. Работает только для local подключений. Удобно для администрирования на самом сервере.

- `scram-sha-256` — современный и рекомендуемый метод для паролей. Пришёл на смену md5, который считается устаревшим и небезопасным.

- `md5` — устаревший метод. В новых версиях PostgreSQL (начиная с 14) scram-sha-256 используется по умолчанию для хранения паролей.

- `cert` — аутентификация по SSL-клиентскому сертификату. Используется для высокобезопасных сред.

- `trust` — никогда не используйте для сетевых подключений. Любой, кто может подключиться, войдёт под любым пользователем без пароля.

- `reject` — явный запрет. Полезен как последняя строка, чтобы «отказ» был виден в файле, а не был следствием отсутствия правила.

## Что обычно меняют в реальной практике и продакшене
1) **Закрывают trust и открытый доступ.** Дефолтная установка часто слишком мягкая; в продакшене все сетевые подключения должны требовать пароль (scram-sha-256) или сертификат.

2) **Переходят с md5 на scram-sha-256.** Это планомерный процесс: сначала меняют password_encryption, затем обновляют хэши паролей, и только потом правят метод в pg_hba.conf.

3) **Включают hostssl для всех TCP-подключений.** Особенно для административных сессий, репликации и мониторинга.

4) **Ограничивают доступ конкретными подсетями (CIDR).** Вместо 0.0.0.0/0 указывают 10.1.0.0/16 или конкретный IP приложения.

5) **Добавляют финальное правило reject.** Это делает политику «запрещено всё, что не разрешено» явной и видимой.

6) **Организуют правила по принципу «узкое — выше, широкое — ниже».** Например: сначала local для админа через peer, затем конкретные приложения с их подсетей через hostssl/scram-sha-256, в конце — reject для всех остальных.

## Как правильно менять и применять

Порядок действий (безопасный):

1) Проверьте текущие правила и их порядок. Полезно выписать для каждого приложения: база, роль, адрес клиента, тип подключения, метод.

2) Сделайте резервную копию файла.

3) Внесите правки. Рекомендуется добавлять новые правила в логически правильное место с учётом приоритета, а не просто в конец, если только новое правило не является самым «широким».

4) Проверьте синтаксис до применения! Это критически важно, потому что опечатка может заблокировать всех клиентов. Используйте системное представление pg_hba_file_rules:

```sql
SELECT line_number, type, database, user_name, address, auth_method, error
FROM pg_hba_file_rules
ORDER BY line_number;
```
Строки с непустым полем error указывают на проблемы в соответствующих строках файла.

5) Примените изменения через reload, а не restart. pg_hba.conf относится к контексту sighup:

```bash
sudo pg_ctlcluster 17 main reload
# или из psql:
SELECT pg_reload_conf();
```
Существующие соединения не разрываются; новые подключения будут проверяться по обновлённым правилам.

6) Обязательно протестируйте новое подключение с того адреса и под той ролью, для которых предназначалось правило. Синтаксическая проверка не гарантирует, что реальный клиент сможет подключиться.

Важное предостережение: если вы правите pg_hba.conf удалённо (например, через SSH-туннель), держите открытой одну локальную административную сессию (через peer или локальный сокет) на время reload. Если новое правило окажется ошибочным, вы не потеряете доступ и сможете откатить изменения.

## Итог

pg_hba.conf — это не «список разрешений», а упорядоченная политика: первое совпадение решает всё, поэтому специфичные правила ставят выше общих, scram-sha-256 и hostssl — для продакшена, pg_hba_file_rules — для проверки перед reload, и всегда оставляйте себе локальный путь для восстановления доступа.

Когда будет достаточная степень осознания pg_hba.conf, имеет смысл разобрать файл pg_ident.conf — он тесно связан с peer и cert и дополняет картину аутентификации.
