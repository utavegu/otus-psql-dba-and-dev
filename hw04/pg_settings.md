Представление pg_settings — это основной «пульт управления» параметрами PostgreSQL. Оно не просто показывает текущие значения, но и содержит всю служебную информацию, необходимую для планирования изменений: контекст, единицы измерения, источник значения и флаг необходимости перезагрузки.

## Как вызвать и что смотреть в первую очередь
Самый информативный запрос для повседневной работы выглядит так:
```sql
SELECT name, setting, unit, context, source, pending_restart
FROM pg_settings
ORDER BY name;
```

Ключевые колонки для планирования изменений:

- context — самое важное поле. Определяет, как и когда можно применить новое значение.

- pending_restart — показывает true, если значение в файле конфигурации уже изменено, но сервер ещё не перезагружен для его применения.

- source — откуда взято текущее значение (default, configuration file, environment variable, session и т.д.). Помогает понять, почему значение отличается от ожидаемого.

- sourcefile / sourceline — конкретный файл и строка, откуда взято значение (доступно суперпользователю или роли с правом pg_read_all_settings).

## Значения поля context: полная карта действий
Значения context расположены в порядке убывания сложности изменения параметра.

### internal — «Трогать нельзя»
- Перевод: Внутренний.

- Что означает: Параметр задан при сборке PostgreSQL или инициализации кластера (initdb). Изменить его через конфигурационные файлы или SQL-команды невозможно.

- Действие: Никакое. Это «константа» для данного экземпляра СУБД.

### postmaster — «Только рестарт»
- Перевод: Почтовый мастер (главный процесс).

- Что означает: Параметр применяется только при старте сервера. Изменение в файле postgresql.conf не вступит в силу, пока вы не выполните полный перезапуск (restart) кластера.

- Действие: restart (например, sudo pg_ctlcluster 17 main restart).

- Важно: Это самый «дорогой» тип изменения, так как требует простоя. pending_restart станет true сразу после правки файла и останется true до перезапуска.

### sighup — «Достаточно reload»
- Перевод: SIGHUP (сигнал «повесить трубку» / перечитать конфигурацию).

- Что означает: Параметр можно изменить в postgresql.conf без перезапуска сервера. Достаточно послать процессу postmaster сигнал SIGHUP (что и делает команда reload), чтобы он перечитал файл и передал новое значение дочерним процессам.

- Действие: reload (например, sudo pg_ctlcluster 17 main reload или SELECT pg_reload_conf();).

- Нюанс: Новое значение подхватят все процессы, но уже запущенные сессии могут продолжать использовать старое значение до своего завершения, если параметр не читается динамически.

### superuser-backend и backend — «Только для новых сессий»
- Перевод: Суперпользовательский/обычный бэкенд (серверный процесс сессии).

- Что означает: Параметр применяется только в момент установления нового соединения. Изменение в postgresql.conf (через reload) не повлияет на уже существующие сессии, но будет применено ко всем новым подключениям.

- Действие: reload для чтения нового значения из файла. Для применения к конкретной сессии — переподключение.

- Разница: superuser-backend может быть изменён в параметрах подключения (например, PGOPTIONS) только суперпользователем или ролью с правом SET. backend — любым пользователем для своей сессии.

### superuser и user — «Можно менять на лету»
- Перевод: Суперпользователь / Пользователь.

- Что означает: Параметр можно изменить в любой момент в рамках текущей сессии с помощью команды SET. Изменения в postgresql.conf (через reload) повлияют на существующие сессии только если в них не было явного SET для этого параметра.

- Действие: SET parameter = value; в текущей сессии. Для глобального применения — reload.

- Разница: superuser может менять только суперпользователь (или роль с соответствующим правом SET). user — любой пользователь для своей сессии.

### Сводная таблица
| Контекст | Действие для применения из файла | Влияние на текущие сессии | Влияние на новые сессии |
| --- | --- | --- | --- |
| `internal` | Невозможно | — | — |
| `postmaster` | restart | ✅ (после рестарта) | ✅ |
| `sighup` | reload | ✅ (обычно) | ✅ |
| `superuser-backend` | reload | ❌ | ✅ |
| `backend` | reload | ❌ | ✅ |
| `superuser` | reload (или SET) | ✅ (если не было SET) | ✅ |
| `user` | reload (или SET) | ✅ (если не было SET) | ✅ |

## Как заранее спланировать изменения
Вы можете заранее узнать контекст любого параметра, который собираетесь менять, и спланировать свои действия. Вот несколько полезных запросов.

1. Узнать контекст конкретного параметра:
```sql
SELECT name, setting, context, pending_restart
FROM pg_settings
WHERE name = 'max_connections'; -- замените на нужный параметр
```

2. Посмотреть все параметры, требующие restart (контекст postmaster):
```sql
SELECT name, setting, pending_restart
FROM pg_settings
WHERE context = 'postmaster'
ORDER BY name;
```

3. Посмотреть все параметры, которые можно применить через reload (контекст sighup):
```sql
SELECT name, setting, pending_restart
FROM pg_settings
WHERE context = 'sighup'
ORDER BY name;
```

4. Проверить, «висят» ли уже какие-то изменения до перезагрузки:
```sql
SELECT name, setting, context
FROM pg_settings
WHERE pending_restart = true;
```

Если этот запрос возвращает строки, значит, в файлах конфигурации уже есть изменения, которые вступят в силу только после restart.

Зная контекст параметра, вы всегда можете ответить на вопрос: «Что мне нужно сделать, чтобы это изменение вступило в силу?» — и избежать неожиданных простоев или, наоборот, ситуаций, когда изменение «не работает» без перезагрузки.
