pg_ident.conf — это, пожалуй, самый «недооценённый» файл в конфигурации PostgreSQL. Если pg_hba.conf отвечает на вопрос «откуда можно подключаться и как проверять», то pg_ident.conf отвечает на вопрос «если внешняя система сказала, что пользователь — это X, то каким пользователем PostgreSQL ему разрешено быть?».

Без этого файла не обходится ни peer-аутентификация на локальном сервере, ни доступ через LDAP/AD, ни Kerberos/GSSAPI, ни клиентские SSL-сертификаты.

## Где лежит pg_ident.conf
По умолчанию файл находится в каталоге данных кластера. Для Ubuntu, кластер 17 это, скорее всего, /var/lib/postgresql/17/main/pg_ident.conf.

Но путь можно переопределить параметром ident_file в postgresql.conf, поэтому надёжнее всего проверить актуальное расположение через psql:

```sql
SHOW ident_file;
```

## Синтаксис и ключевые поля
Файл состоит из строк вида:
```text
MAPNAME   SYSTEM-USERNAME   PG-USERNAME
```

- MAPNAME — произвольное имя карты (набора правил). Именно это имя ты потом указываешь в pg_hba.conf в опции map=имя_карты.

- SYSTEM-USERNAME — имя пользователя, которое вернула внешняя система аутентификации (ОС-пользователь для peer, DN для cert, principal для GSSAPI и т.д.).

- PG-USERNAME — имя роли в PostgreSQL, под которой этому пользователю разрешено подключаться.

### Ключевые возможности, которые стоит знать:

- Одна карта — много строк. Один и тот же MAPNAME можно повторять сколько угодно раз, задавая разные пары «системный пользователь → роль PostgreSQL».

- all в поле PG-USERNAME означает, что системный пользователь может зайти под любой существующей ролью. Использовать с крайней осторожностью.

- "+" перед именем роли означает «любая роль, которая является участником (прямо или косвенно) этой роли».

- Регулярные выражения. Если SYSTEM-USERNAME начинается с /, остаток поля трактуется как регулярное выражение. Можно использовать захват группы и подставлять его в PG-USERNAME через \1. Например, чтобы отбросить домен: /^(.*)@mydomain\.com$ \1.

- include / include_dir — как и в pg_hba.conf, можно подключать другие файлы.

Пример из документации:
```text
# MAPNAME   SYSTEM-USERNAME   PG-USERNAME
omicron     bryanh            bryanh
omicron     ann               ann
omicron     robert            bob        # ОС-пользователь robert может зайти как роль bob
omicron     bryanh            guest1     # bryanh может зайти и как guest1
```

## Что обычно меняют для продакшена

Сам файл напрямую меняют редко — обычно его дополняют под конкретный сценарий аутентификации:

1) Сопоставление для peer. На сервере есть системный пользователь deploy, а роль в БД называется app_owner. Без карты peer не пустит deploy под ролью app_owner — придётся либо переименовывать роль, либо использовать карту.

2) Интеграция с LDAP/AD или Kerberos. Корпоративные логины (ivan.petrov@corp.local) могут не совпадать с именами ролей в PostgreSQL (ivan_petrov). Карта приводит их к единому виду, часто с помощью регулярных выражений.

3) Аутентификация по клиентским сертификатам (cert). DN сертификата (CN=John Doe, OU=Users, DC=example, DC=com) слишком длинный для имени роли. Карта извлекает из него CN или приводит к нужному виду.

4) Принцип наименьших привилегий. В продакшене избегают all в PG-USERNAME. Каждая строка карты должна явно разрешать конкретному системному пользователю вход только под конкретной ролью. all допустим разве что в изолированной тестовой среде.

5) Явное указание map= в pg_hba.conf. По умолчанию peer и некоторые другие методы используют неявную карту с именем, совпадающим с именем пользователя ОС. В продакшене предпочитают задавать карту явно (map=myapp_peer), чтобы поведение было предсказуемым и не зависело от совпадения имён.

## Как правильно применить изменения

pg_ident.conf относится к контексту sighup: он перечитывается при старте и при получении сигнала SIGHUP. Значит, для применения изменений не нужен рестарт — достаточно reload.

Безопасный порядок действий:

1) Проверь текущее содержимое и синтаксис до применения. Есть системное представление pg_ident_file_mappings, которое показывает, как PostgreSQL разобрал файл в его текущем состоянии на диске (даже если сервер ещё не перечитывал его). Строки с непустым полем error указывают на проблемы:

```sql
SELECT line_number, map_name, sys_name, pg_username, error
FROM pg_ident_file_mappings
ORDER BY line_number;
```

Это аналог pg_hba_file_rules для pg_ident.conf. Обязательно проверь это перед reload: синтаксическая ошибка в карте может сломать аутентификацию для тех подключений, которые на неё полагаются.

2) Внеси правки (с резервной копией файла, как обычно).

3) Примени через reload:

```bash
sudo pg_ctlcluster 17 main reload
# или из psql:
SELECT pg_reload_conf();
```

4) Проверь реальное подключение тем способом, для которого предназначена карта (например, psql -U нужная_роль через Unix-сокет для peer, или подключение по LDAP/GSSAPI). pg_ident_file_mappings показывает только то, что файл разобран, а не то, что конкретная пара «системный пользователь → роль» действительно сработает в данном сценарии.

## Как откатить изменения

Откат здесь такой же, как и для pg_hba.conf:

- Вернуть файл из резервной копии (или удалить добавленные строки вручную).

- Выполнить reload тем же способом.

- Проверить pg_ident_file_mappings — в нём не должно остаться строк с error, а карта должна снова содержать только прежние правила.

Если правка была сделана удалённо и ты рискуешь потерять доступ, держи открытой одну локальную сессию (через peer или Unix-сокет) до тех пор, пока не убедишься, что новое подключение работает. Это универсальное правило для любых изменений в цепочке аутентификации.

## Итог в одной фразе

pg_ident.conf — это слой сопоставления имён: он нужен только тогда, когда имя, которое вернула внешняя система (ОС, LDAP, Kerberos, сертификат), не совпадает с именем роли PostgreSQL; меняется он через явные карты map=, проверяется через pg_ident_file_mappings до reload, а в продакшене строится по принципу «явно разрешить конкретную пару», без all и без надежды на неявные совпадения.
