Транзакция — это действительно логическая единица работы, которая выполняется по принципу «всё или ничего» между BEGIN и COMMIT/ROLLBACK. И ты прав, что при работе через ORM ошибка обычно приводит к полному откату для сохранения консистентности.

Однако в PostgreSQL (и в реляционных СУБД в целом) эта тема гораздо глубже и интереснее. Давай разберём ключевые концепции, которые превращают твоё базовое понимание в полноценную картину.

## Фундамент: Свойства ACID

Твоё описание — это, по сути, свойства Атомарности (Atomicity) и Согласованности (Consistency). Вместе с ними выделяют ещё два важнейших свойства, которые гарантируют надёжность транзакций:

- Атомарность (Atomicity): «Всё или ничего». Если транзакция прерывается, все её изменения откатываются.

- Согласованность (Consistency): Транзакция переводит базу данных из одного корректного состояния в другое, не нарушая установленные правила и ограничения (например, внешние ключи или проверки CHECK).

- Изоляция (Isolation): Результат параллельного выполнения транзакций должен быть таким же, как если бы они выполнялись последовательно, одна за другой. Это, пожалуй, самая сложная и интересная часть.

- Долговечность (Durability): Если транзакция успешно зафиксирована (COMMIT), её изменения не будут потеряны даже в случае сбоя питания или падения сервера.

## Как PostgreSQL обеспечивает изоляцию: MVCC

В отличие от многих других СУБД, PostgreSQL использует не блокировки для управления параллельным доступом (хотя они тоже есть), а MVCC (Multiversion Concurrency Control) — многоверсионный механизм.

Ключевая идея MVCC в том, что при чтении данных транзакция видит не текущее состояние базы, а её снимок (snapshot) на определённый момент времени. Когда одна транзакция обновляет строку, PostgreSQL не перезаписывает старую, а создаёт новую версию этой строки. Старая версия остаётся доступной для транзакций, чей снимок был сделан до обновления.

Главное преимущество: Благодаря MVCC чтение никогда не блокирует запись, а запись никогда не блокирует чтение. Это обеспечивает высокую степень параллелизма.

## Уровни изоляции: Выбор компромисса

Стандарт SQL определяет четыре уровня изоляции, которые решают, какие аномалии могут возникать при параллельной работе. PostgreSQL поддерживает их все, но с важными оговорками.

|Уровень изоляции \ Аномалия|Потерянное обновление (Lost update)|Грязное чтение (Dirty Read)|Неповторяющееся чтение (Nonrepeatable Read)|Фантомное чтение (Phantom Read)|Аномалия сериализации (Serialization Anomaly)|
|---|---|---|---|---|---|
|Read Committed (Чтение зафиксированных данных) (по умолчанию)|Невозможно|Невозможно|Возможно|Возможно|Возможно|
|Read Uncommitted (Чтение незафиксированных данных)|Невозможно|Допускается (но не в PG)|Возможно|Возможно|Возможно|
|Repeatable Read (Повторяемое чтение)|Невозможно|Невозможно|Невозможно|Допускается (но не в PG)|Возможно|
|Serializable (Сериализуемость)|Невозможно|Невозможно|Невозможно|Невозможно|Невозможно|

### Что важно знать о реализации в PostgreSQL:

- Read Uncommitted → Read Committed: В PostgreSQL «грязное чтение» невозможно в принципе. Поэтому уровень Read Uncommitted внутри просто превращается в Read Committed.

- Read Committed (уровень по умолчанию): Каждая отдельная команда внутри транзакции видит снимок данных на момент своего начала. Поэтому два одинаковых SELECT в одной транзакции могут вернуть разные результаты, если между ними другая транзакция зафиксировала изменения.

- Repeatable Read: Снимок данных создаётся один раз при первой команде транзакции, и все последующие команды видят одно и то же состояние. Это решает проблему неповторяющегося чтения. Более того, в PostgreSQL этот уровень строже стандарта и также предотвращает фантомное чтение.

- Serializable: Самый строгий уровень. Он гарантирует, что результат параллельного выполнения транзакций будет эквивалентен какому-то последовательному порядку их выполнения. Однако за это приходится платить производительностью и возможными ошибками сериализации, которые требуют повторной попытки выполнения транзакции.

## Обработка ошибок: ROLLBACK vs SAVEPOINT

Здесь кроется важный нюанс, который часто упускают. В PostgreSQL любая ошибка внутри транзакции (например, нарушение ограничения) переводит всю транзакцию в состояние «прервано» (aborted). После этого никакие команды, кроме ROLLBACK, выполняться не будут.

Именно здесь на помощь приходят точки сохранения (SAVEPOINT):

SAVEPOINT my_point; — создаёт точку, к которой можно вернуться.

ROLLBACK TO SAVEPOINT my_point; — откатывает только те изменения, которые были сделаны после этой точки, и восстанавливает работоспособность транзакции. Вы можете продолжить выполнение транзакции с этого места.

```sql
BEGIN;
  INSERT INTO users (name) VALUES ('Alice'); -- Это изменение сохранится

  SAVEPOINT sp1;

  INSERT INTO users (name) VALUES ('Bob');
  -- Ошибка! Например, нарушение уникальности имени 'Bob'
  -- Транзакция переходит в состояние "прервано"

  ROLLBACK TO SAVEPOINT sp1; -- Откатывает только попытку вставить 'Bob'
  -- Транзакция снова активна, и вставка 'Alice' всё ещё в силе

  INSERT INTO users (name) VALUES ('Charlie'); -- Это изменение тоже сохранится
COMMIT; -- Фиксирует 'Alice' и 'Charlie'
```

Этот приём часто используется в ORM (например, SQLAlchemy) для обработки ожидаемых ошибок (например, IntegrityError при дублировании) без потери всей транзакции.

## Типичные ошибки и практические рекомендации

Забытый COMMIT или ROLLBACK: «Классика жанра». Транзакция остаётся открытой, удерживая блокировки и ресурсы, что может заблокировать другие операции. Решение: Всегда явно завершайте транзакцию.

Неверный выбор уровня изоляции: Использование READ COMMITTED (по умолчанию) для сложных отчётов может привести к противоречивым данным из-за параллельных изменений. Использование SERIALIZABLE везде может неоправданно снизить производительность и вызвать ошибки сериализации. Решение: Выбирайте уровень изоляции осознанно, исходя из задачи.

Взаимные блокировки (Deadlocks): Две транзакции могут заблокировать друг друга, ожидая ресурсы, которые удерживает другая. PostgreSQL автоматически обнаруживает deadlock и прерывает одну из транзакций с ошибкой. Решение: Старайтесь, чтобы транзакции обращались к ресурсам (таблицам, строкам) в одном и том же порядке.

Использование COMMIT внутри PL/pgSQL функций: В функциях (FUNCTION) использовать COMMIT или ROLLBACK нельзя — это вызовет ошибку. Это разрешено только в процедурах (PROCEDURE).

Твой стартовый посыл был абсолютно верным. Надеюсь, это небольшое погружение поможет тебе увидеть всю картину целиком: от простого «всё или ничего» до управления видимостью данных через MVCC и выбора правильного уровня изоляции для конкретной задачи.

Если захочешь разобрать какой-то из этих пунктов подробнее на примерах (например, аномалии на разных уровнях изоляции или работу SAVEPOINT в SQLAlchemy), дай знать.

## Виды аномалий

Аномалия транзакций (феномены, аномалии конкурентного доступа) — это нежелательное явление, которое может возникнуть при параллельном выполнении нескольких транзакций и из-за которого результат работы отличается от того, как если бы эти транзакции выполнялись последовательно, одна за другой, — либо нарушается логическая согласованность данных.

Проще говоря: это «симптом болезни» конкурентного доступа. Когда несколько транзакций одновременно трогают одни и те же данные, между ними возникают «помехи», и данные могут стать противоречивыми. Аномалия — это описание конкретного вида такой помехи.

Ключевая мысль: аномалия — это не ошибка в коде и не баг базы. Это принципиально возможный сценарий при параллельной работе, который нужно либо принять как допустимый, либо предотвратить.

### Потерянное обновление (Lost Update)

- Что это такое: Это ситуация, когда две транзакции читают одни и те же данные, а затем обе пытаются их обновить. В результате одно из обновлений «затирает» другое, и изменения, сделанные одной из транзакций, теряются.

- «Потерянное чтение» vs «Потерянное обновление»: «Потерянное чтение» — это, вероятно, неточный перевод или синоним, который иногда используют для описания последствий «потерянного обновления».

- Почему для всех уровней «Невозможно»: В твоих данных указано, что «Потерянное чтение» невозможно на всех уровнях. Это логично, если под ним понимать именно потерю уже прочитанных данных (чего в PostgreSQL быть не может). Однако «Потерянное обновление» — это реальная и очень важная аномалия, которая возможна на уровне Read Committed (уровень по умолчанию) и которую PostgreSQL автоматически предотвращает на уровне Repeatable Read.

Поэтому в нашей таблице мы будем использовать стандартные четыре аномалии из документации (Dirty Read, Nonrepeatable Read, Phantom Read, Serialization Anomaly), но помнить, что «Потерянное обновление» — это их важное практическое следствие.

#### Что такое «Потерянное чтение» и почему его нет в стандартах?

Твоё предположение, что это ошибка в презентации, скорее всего, верно. В официальной документации PostgreSQL и в стандарте SQL (на который она опирается) такой аномалии нет. Стандартный набор «феноменов», которые запрещены на разных уровнях изоляции, включает:

- Dirty Read (Грязное чтение)

- Nonrepeatable Read (Неповторяющееся чтение)

- Phantom Read (Фантомное чтение)

- Serialization Anomaly (Аномалия сериализации)

Термин «Потерянное чтение» (Lost Read) не входит в этот перечень. В некоторых источниках можно встретить мнение, что «Потерянное обновление» (Lost Update) — это не аномалия чтения, а конфликт записи-записи (write-write conflict). Возможно, автор презентации, услышав про «Lost Update», попытался сконструировать симметричный термин «Lost Read», но это не прижилось в индустрии.

Вывод: Можешь смело игнорировать «Потерянное чтение» как отдельную аномалию. Твои данные о том, что она «невозможна» на всех уровнях, — это просто следствие того, что такого явления в общепринятой теории нет. А вот «Потерянное обновление» — это реальная и очень важная проблема, которую мы и разберём.

### Аномалия №1: Dirty Read (Грязное чтение)

#### Что это такое?

Грязное чтение — это ситуация, когда транзакция читает данные, которые были изменены другой транзакцией, но ещё не зафиксированы (COMMIT не выполнен). То есть вы читаете «грязные», промежуточные данные, которые в любой момент могут быть откачены (ROLLBACK).

#### Пример (гипотетический для PostgreSQL)
Представь, что такой уровень изоляции, как Read Uncommitted, в PostgreSQL реально работал бы (спойлер: нет, но об этом в сообщении про этот уровень).
```sql
-- Сессия A (писатель)                          -- Сессия B (читатель)
BEGIN;                                           BEGIN;
UPDATE accounts SET balance = 0 WHERE id = 1;
-- (пока не сделал COMMIT!)                     SELECT balance FROM accounts WHERE id = 1;
                                                 -- Прочитал: 0 (!)

ROLLBACK; -- Сессия A откатывает изменение
                                                 -- Сессия B думает, что баланс = 0, 
                                                 -- но на самом деле он снова 1000
```


Сессия B прочитала значение 0, которого никогда не существовало в зафиксированном состоянии базы. Если на основе этого «грязного» значения она примет решение (например, отправит уведомление «счёт пуст» или спишет комиссию), это приведёт к ошибке, которую потом невозможно исправить.

#### Почему в PostgreSQL это невозможно?

PostgreSQL не поддерживает грязное чтение ни на каком уровне изоляции, включая Read Uncommitted (который внутри просто превращается в Read Committed). Это следствие архитектуры MVCC: читатель видит только те версии строк, которые были зафиксированы до начала его снимка (snapshot). Незафиксированные изменения других транзакций для него невидимы — они лежат в «теневой» области и не попадают в снимок.

#### Зачем тогда вообще знать про эту аномалию?

- Понимание эволюции стандартов. Dirty Read — это исторически первая аномалия, ради которой придумали уровни изоляции. Стандарт SQL описывает её, и в некоторых других СУБД (например, в старых версиях MySQL с MyISAM, или в SQL Server при определённых настройках) она реально возможна. Знание термина помогает читать документацию и сравнивать PostgreSQL с другими базами.

- Понимание, почему Read Committed — это «минимум». Тот факт, что PostgreSQL не позволяет грязное чтение даже на самом слабом уровне, — это важное свойство, которое отличает его от «теоретического» стандарта. Это даёт уверенность: какие бы данные вы ни читали, вы никогда не увидите «фантомных» незафиксированных значений.

- Собеседования и общение с коллегами. Термин стандартный, и его полезно знать, даже если в PostgreSQL вы с ним не столкнётесь.

#### Ключевая мысль

Dirty Read — это чтение незафиксированных изменений. В PostgreSQL это невозможно by design, благодаря MVCC. Поэтому в реальной работе вы о нём не думаете — но понимание этой аномалии даёт вам базу для понимания остальных, более тонких проблем.

Следующая аномалия Nonrepeatable Read (Неповторяющееся чтение). Она уже реально возможна в PostgreSQL на уровне по умолчанию, и с ней программисты сталкиваются постоянно.

### Аномалия №2: Nonrepeatable Read (Неповторяющееся чтение)

#### Что это такое?

Неповторяющееся чтение — это ситуация, когда внутри одной и той же транзакции вы читаете одну и ту же строку дважды и получаете разные значения, потому что между двумя чтениями другая транзакция изменила эту строку и зафиксировала изменения (COMMIT).

Важно: речь именно о повторном чтении одной и той же строки в рамках одной транзакции. Если вы прочитали строку в одной транзакции, а потом в другой — это нормально и не является аномалией.

#### Почему это возможно на Read Committed

На уровне Read Committed (уровень по умолчанию в PostgreSQL) каждая отдельная команда видит снимок базы на момент своего начала. Поэтому два SELECT в одной транзакции могут «увидеть» разные состояния одной строки, если между ними кто-то зафиксировал изменение.

#### Практический пример: «Проверил — а потом оно изменилось»

Ситуация: Транзакция проверяет лимит на счёте, принимает решение, а затем перечитывает баланс для логирования. Между чтениями другая транзакция пополняет счёт.

```sql
-- Сессия A (наша транзакция)                    -- Сессия B (параллельная)
BEGIN; -- Read Committed
SELECT balance FROM accounts WHERE id = 1;
-- Прочитали: 1000

                                                 BEGIN;
                                                 UPDATE accounts SET balance = 1500 WHERE id = 1;
                                                 COMMIT; -- зафиксировала 1500

SELECT balance FROM accounts WHERE id = 1;
-- Прочитали: 1500 (!) — хотя это та же транзакция и та же строка

-- В логе: "Баланс был 1000, стал 1500" — но мы не делали никаких изменений!
COMMIT;
```

Внутри одной транзакции мы увидели два разных значения одной и той же строки. Логика, построенная на первом значении, может противоречить второму. Это и есть неповторяющееся чтение.

#### Практический сценарий: когда это реально кусается

Самый частый случай — многошаговые вычисления внутри одной транзакции, где результат одного SELECT используется в логике, а второй SELECT — для проверки, логирования или финального расчёта.

Пример из жизни — генерация отчёта:

`SELECT SUM(amount) FROM payments WHERE ...` — считаем итог.

(параллельно кто-то добавляет платёж и коммитит)

`SELECT COUNT(*) FROM payments WHERE ...` — считаем количество для среднего.

Средний платёж = сумма / количество — но сумма и количество посчитаны по разным состояниям данных. Отчёт внутренне противоречив.

Пример из жизни — «проверка и подтверждение»:

Читаем статус заказа: 'new'.

Проверяем бизнес-правило: «если new, то можно отменить».

(параллельно заказ перевели в 'shipped' и закоммитили)

Перечитываем статус перед отменой — уже 'shipped', и логика ломается: мы проверяли одно, а действуем на основе другого.

#### Чем отличается от Lost Update

Это важное различие, их часто путают:

- Nonrepeatable Read — про чтение: два чтения одной строки дают разный результат. Записи может вообще не быть.

- Lost Update — про запись: два обновления одной строки, и одно затирает другое. Это конфликт «запись-запись».

Nonrepeatable Read может быть «первым звеном» цепочки, которая приводит к Lost Update (прочитал → вычислил → записал), но это разные явления.

#### Как предотвратить

Поднять уровень изоляции до Repeatable Read. В PostgreSQL на этом уровне снимок создаётся один раз при первой команде транзакции, и все последующие SELECT видят одно и то же состояние. Неповторяющееся чтение становится невозможным.

Заблокировать строку на чтение: SELECT ... FOR SHARE. Другие транзакции не смогут изменить строку, пока вы не завершите свою.

#### Ключевая мысль

Nonrepeatable Read — это «я дважды прочитал одну строку в одной транзакции и получил разные значения». В PostgreSQL он возможен на Read Committed (уровень по умолчанию) и предотвращается на Repeatable Read. Задумываться о нём стоит всякий раз, когда внутри одной транзакции есть несколько SELECT одной и той же строки/таблицы, между которыми возможны параллельные изменения, и когда результат первого чтения влияет на логику.

Следующая — Phantom Read (Фантомное чтение). Она похожа на Nonrepeatable Read, но с важным отличием: речь не об изменении существующей строки, а о появлении новых строк, подходящих под условие.

### Аномалия №2: Nonrepeatable Read (Неповторяющееся чтение)

Аномалия №3: Phantom Read (Фантомное чтение)
Что это такое?
Фантомное чтение — это ситуация, когда внутри одной и той же транзакции вы выполняете один и тот же запрос с условием (например, WHERE) дважды и получаете разный набор строк: между двумя выполнениями другая транзакция добавила (или удалила) строки, подходящие под это условие, и зафиксировала изменения.

Ключевое слово — «фантом»: появляются или исчезают целые строки, которых при первом чтении не было (или которые были). Это не изменение значения в существующей строке (как в Nonrepeatable Read), а изменение состава множества строк, удовлетворяющих условию.

#### Чем отличается от Nonrepeatable Read

Это самое важное различие, и его часто путают:

||Nonrepeatable Read|Phantom Read|
|---|---|---|
|Что меняется|Значение в существующей строке|Появляются/исчезают строки, подходящие под условие|
|Пример запроса|`SELECT balance FROM accounts WHERE id = 1`|`SELECT * FROM orders WHERE status = 'new'`|
|Что произошло|Кто-то сделал `UPDATE` строки `id = 1`|Кто-то сделал `INSERT` новой строки со `status = 'new'` (или `DELETE` существующей)|
|Аналогия|Вы смотрите на один и тот же стул, но он перекрашен|Вы смотрите на комнату, и в ней появился новый стул|

Простая мнемоника: Nonrepeatable Read — про изменение строки, Phantom Read — про изменение множества строк.

#### Почему это возможно на Read Committed

На уровне Read Committed каждая команда видит свежий снимок базы на момент своего начала. Если между двумя SELECT с условием другая транзакция вставила строку, подходящую под это условие, и закоммитила её — второй SELECT её увидит. Для вас это «фантом»: строки не было, и вдруг она есть.

#### Практический пример: «Считаю — а счётчик растёт»
Ситуация: Транзакция проверяет, не превышен ли лимит заказов, а затем подсчитывает количество для отчёта.
```sql
-- Сессия A (наша транзакция)                         -- Сессия B (параллельная)
BEGIN; -- Read Committed

-- Шаг 1: Проверяем, сколько активных заказов у клиента
SELECT COUNT(*) FROM orders WHERE customer_id = 42 AND status = 'new';
-- Результат: 5. Лимит — 10. Всё ок, можно продолжать.

                                                      BEGIN;
                                                      INSERT INTO orders (customer_id, status) VALUES (42, 'new');
                                                      -- ... и ещё 6 таких же ...
                                                      COMMIT; -- теперь у клиента 11 активных заказов

-- Шаг 2: Финальная проверка перед оформлением
SELECT COUNT(*) FROM orders WHERE customer_id = 42 AND status = 'new';
-- Результат: 11 (!) — лимит уже превышен, хотя мы только что проверили

COMMIT;
```

Между двумя COUNT(*) появились «фантомные» строки. Логика, построенная на первом результате (5 < 10), оказалась неверной к моменту второго чтения (11 > 10).

#### Практический сценарий: когда это реально кусается

1. Проверка лимитов и квот.
«Проверю, не превысил ли пользователь лимит, и если нет — добавлю ещё одну запись». Между проверкой и вставкой кто-то добавляет записи — лимит превышен, но вы этого «не видели».

2. Отчёты и агрегаты.
«Посчитаю сумму за период, потом количество за период». Между запросами кто-то добавил транзакцию — сумма и количество посчитаны по разным наборам строк. Отчёт противоречив.

3. Логика «проверил — сделал».
«Проверю, есть ли запись с таким ключом, и если нет — вставлю». Между проверкой и вставкой кто-то вставил такую же запись. Вы этого не увидели (фантом), и ваша вставка либо упадёт на уникальном индексе, либо создаст дубликат (если индекса нет). Это классический race condition, и Phantom Read — его «читательская» сторона.

#### Важный нюанс: в PostgreSQL на Repeatable Read фантомов НЕТ

Это ключевое отличие PostgreSQL от «теоретического» стандарта SQL. По стандарту:

- Read Committed — фантомы возможны.

- Repeatable Read — фантомы возможны (по стандарту!).

- Serializable — фантомы невозможны.

Но в PostgreSQL благодаря MVCC:

- Read Committed — фантомы возможны.

- Repeatable Read — фантомы невозможны (!). PostgreSQL на этом уровне даёт более сильную гарантию, чем требует стандарт.

- Serializable — фантомы невозможны.

Поэтому в таблице «уровень × аномалия» для PostgreSQL ячейка Repeatable Read + Phantom Read — это «невозможно», хотя в стандартной таблице SQL там стоит «возможно». Это важное практическое знание: в PostgreSQL Repeatable Read защищает и от фантомов тоже, что делает его очень удобным для отчётов и многошаговой логики.

#### Как предотвратить

Поднять уровень изоляции до Repeatable Read. В PostgreSQL это решает проблему фантомов полностью: снимок создаётся один раз, и все SELECT видят одно и то же множество строк.

Использовать SERIALIZABLE — самый строгий уровень, гарантирует отсутствие фантомов (и вообще любых аномалий), но ценой возможных ошибок сериализации и повторов.

Заблокировать диапазон/таблицу через SELECT ... FOR UPDATE / FOR SHARE или явные блокировки (LOCK TABLE), но это грубее и снижает параллелизм.

####  Ключевая мысль

Phantom Read — это «я дважды выполнил один и тот же запрос с условием и получил разный набор строк», потому что кто-то вставил/удалил подходящие строки. В PostgreSQL он возможен на Read Committed (уровень по умолчанию) и невозможен на Repeatable Read — это важное усиление относительно стандарта SQL. Задумываться о нём стоит всякий раз, когда внутри одной транзакции есть несколько запросов с условием (WHERE, COUNT, EXISTS), между которыми возможны вставки/удаления, и когда результат первого запроса влияет на логику.

Следующая — Lost Update (Потерянное обновление). Мы её уже частично разбирали в контексте Read Committed, но теперь посмотрим на неё как на отдельную аномалию: что это, почему это не «чтение», а конфликт «запись-запись», и как она связана с остальными.

### Аномалия №4: Lost Update (Потерянное обновление)

#### Что это такое?

Потерянное обновление — это ситуация, когда две (или более) транзакции читают одну и ту же строку, затем обе обновляют её на основе прочитанного, и в результате изменения одной из них затираются изменениями другой. Обновление «теряется» — как будто его никогда не было.

Мы уже касались её в контексте Read Committed, но теперь посмотрим на неё как на отдельную аномалию — и сразу проясним важный нюанс, который часто упускают.

#### Почему это «не такая» аномалия, как предыдущие

Обрати внимание на важное отличие от трёх предыдущих:

- Dirty / Nonrepeatable / Phantom Read — это аномалии чтения. Вы читаете данные, и они «ведут себя странно» (незафиксированные, меняются, появляются/исчезают строки). Записи может вообще не быть.

- Lost Update — это аномалия записи (write-write conflict). Проблема не в том, что вы прочитали что-то не то, а в том, что два обновления конкурируют за одну строку, и одно затирает другое.

Это важное концептуальное различие: в стандарте SQL Lost Update иногда выносят отдельно от «феноменов чтения», потому что это конфликт запись-запись, а не чтение. Но по последствиям (потеря данных) — это одна из самых опасных аномалий на практике.

#### Пример: «Куда пропали деньги?»

Ситуация: На счёте 1000. Две транзакции одновременно пытаются списать по 200. Ожидаемый итог — 600.

```sql
-- Сессия A                                          -- Сессия B
BEGIN; -- Read Committed                              BEGIN; -- Read Committed

-- Шаг 1: обе читают баланс
SELECT balance FROM accounts WHERE id = 1;            SELECT balance FROM accounts WHERE id = 1;
-- обе прочитали: 1000                                 -- обе прочитали: 1000

-- Шаг 2: обе вычисляют новый баланс у себя в приложении
-- A: 1000 - 200 = 800                                 -- B: 1000 - 200 = 800

-- Шаг 3: обе записывают
UPDATE accounts SET balance = 800 WHERE id = 1;
                                                       -- B ждёт, пока A закоммитит
COMMIT; -- A зафиксировала 800

                                                       UPDATE accounts SET balance = 800 WHERE id = 1;
                                                       COMMIT; -- B зафиксировала 800

-- Итог: 800, хотя ожидалось 600. Списание B «потерялось».
```

Обрати внимание на коварство: обе транзакции завершились успешно (COMMIT), ошибок нет, база данных консистентна с точки зрения своих ограничений. Но бизнес-данные неверны: одно списание просто исчезло.

#### Почему это возможно на Read Committed

На уровне Read Committed:

При UPDATE PostgreSQL блокирует строку от других записей — поэтому B ждёт, пока A не закоммитит.

Но когда A закоммитила, B не перечитывает строку автоматически. Она просто выполняет свой UPDATE ... SET balance = 800, используя значение 800, которое вычислила заранее на основе устаревшего чтения (1000).

В итоге B записывает 800, затирая результат A.

Ключевой момент: блокировка на запись не спасает от Lost Update, если логика «прочитал → вычислил → записал» разнесена по времени. PostgreSQL не знает, что 800 в вашем UPDATE — это результат вычисления на основе старого значения. Для него это просто новое значение.

#### Практические сценарии: когда это реально кусается

1. Счётчики и балансы.
SELECT balance → balance = balance - amount в приложении → UPDATE. Классика. Потерянные списания, потерянные пополнения.

2. Счётчики просмотров/лайков.
SELECT views → views + 1 в приложении → UPDATE. Под нагрузкой часть инкрементов теряется. Счётчик «недосчитывает».

3. Инвентарь и резервирование.
SELECT quantity → проверка «хватает ли» → quantity = quantity - n → UPDATE. Два заказа могут «зарезервировать» один и тот же товар.

4. Редактирование документов/профилей.
Пользователь A и B одновременно открыли профиль, оба что-то поправили, оба сохранили. Правки A затираются правками B (или наоборот). Это тот же Lost Update, просто на уровне пользовательского интерфейса.

5. Статусные переходы.
SELECT status → проверка «можно ли перевести» → UPDATE status. Между проверкой и обновлением кто-то уже перевёл статус. Ваш переход затирает чужой.

#### Как предотвратить (три подхода, каждый со своим компромиссом)

#### Подход 1: Атомарный UPDATE (лучший, когда применим)
Если бизнес-логику можно выразить в самом SQL, не вынося вычисление в приложение:
```sql
-- Плохо (Lost Update возможен):
-- SELECT balance;  -- 1000
-- UPDATE accounts SET balance = 800 WHERE id = 1;

-- Хорошо (атомарно, Lost Update невозможен):
UPDATE accounts SET balance = balance - 200 WHERE id = 1;
```

Здесь balance - 200 вычисляется внутри базы, под блокировкой строки. PostgreSQL сам сериализует два таких UPDATE: B дождётся A, потом выполнит balance - 200 уже от нового значения. Итог — 600. ✅

- Плюс: просто, быстро, без блокировок на чтение.

- Минус: подходит только когда логику можно выразить одним SQL-выражением. Для сложных вычислений (с проверками, ветвлениями) — не всегда.

#### Подход 2: Пессимистичная блокировка (SELECT ... FOR UPDATE)
Явно блокируем строку на время транзакции:

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE; -- блокируем строку
-- ... вычисляем новый баланс в приложении ...
UPDATE accounts SET balance = 800 WHERE id = 1;
COMMIT;
```

Пока A держит блокировку, B ждёт на своём SELECT ... FOR UPDATE. Когда A закоммитит, B прочитает уже новое значение (800), вычислит от него (800 - 200 = 600) и запишет 600. ✅

- Плюс: работает для любой сложной логики, явно и предсказуемо.

- Минус: другие транзакции ждут; при долгих транзакциях — падение параллелизма; риск дедлоков (нужно соблюдать порядок блокировок).

#### Подход 3: Оптимистичная блокировка (версионирование)
Не блокируем, а проверяем, не изменилось ли с момента чтения:

```sql
-- Читаем вместе с версией:
SELECT balance, version FROM accounts WHERE id = 1; -- balance=1000, version=1

-- Обновляем, только если версия не менялась:
UPDATE accounts
SET balance = 800, version = version + 1
WHERE id = 1 AND version = 1;

-- Если обновлено 0 строк — кто-то успел раньше. Приложение должно
-- перечитать данные и повторить попытку (retry).
```

- Плюс: нет блокировок на чтение, высокая параллельность.

- Минус: нужно добавлять колонку version, обрабатывать конфликты и ретраи в приложении; под высокой конкуренцией — много ретраев.

#### Подход 4: Уровень изоляции Repeatable Read (в PostgreSQL)

В PostgreSQL на уровне Repeatable Read Lost Update предотвращается автоматически, но специфическим образом: если транзакция пытается обновить строку, которая была изменена и закоммичена другой транзакцией после начала вашей, PostgreSQL выдаёт ошибку:

```
ERROR: could not serialize access due to concurrent update
```

Транзакция прерывается, и приложение должно её повторить (retry).

- Плюс: не нужно менять логику запросов — база сама защищает.

- Минус: появляются ошибки, которые нужно обрабатывать и ретраить; под нагрузкой — много повторов.

Важный нюанс: в некоторых СУБД (например, в Oracle или SQL Server на некоторых уровнях) Repeatable Read может «тихо» перечитать и применить обновление. В PostgreSQL — нет: он не пытается «угадать» вашу логику, а честно сообщает о конфликте и просит повторить. Это важное отличие, которое стоит помнить.

#### Ключевая мысль

Lost Update — это конфликт записи, а не чтения: две транзакции читают строку, обе обновляют на основе прочитанного, и одно обновление затирает другое. В PostgreSQL он возможен на Read Committed и предотвращается на Repeatable Read (через ошибку сериализации + retry). Задумываться о нём стоит всякий раз, когда в коде есть паттерн «прочитал → вычислил в приложении → записал» для одной и той же строки. Лучшее лекарство — по возможности атомарный UPDATE, а если логика сложная — SELECT ... FOR UPDATE или оптимистичная блокировка с версией.

Следующая — последняя аномалия: Serialization Anomaly (Аномалия сериализации). Она самая тонкая и «неочевидная»: данные по отдельности консистентны, но вся последовательность транзакций даёт результат, невозможный ни при каком последовательном выполнении.

### Аномалия №5: Serialization Anomaly (Аномалия сериализации)

#### Что это такое?

Аномалия сериализации — это самая тонкая и трудноуловимая аномалия. Она возникает, когда группа транзакций завершается успешно (COMMIT), и каждая из них по отдельности выглядит корректной, но итоговое состояние базы данных невозможно получить ни при каком последовательном порядке выполнения этих транзакций (одна за другой).

Проще говоря: вы смотрите на результат и понимаете — «так не могло бы быть, если бы эти транзакции выполнялись по очереди». При этом ни одна из транзакций не нарушила никаких ограничений (уникальность, внешние ключи и т.д.), и обе они зафиксировали свои изменения.

#### Чем это отличается от всего, что мы разбирали

Все предыдущие аномалии (Dirty Read, Nonrepeatable Read, Phantom Read, Lost Update) можно увидеть внутри одной транзакции или на уровне одной строки. Аномалия сериализации — это свойство целой группы транзакций. Отдельно взятая транзакция может быть абсолютно логичной и корректной. Проблема возникает именно в их комбинации.

Именно поэтому это самая «глубокая» аномалия: она требует от вас мыслить не «что видит моя транзакция», а «что произойдёт, если моя транзакция и чья-то ещё выполнятся одновременно».

#### Классический пример: «Перекос записи» (Write Skew)

Самый простой и наглядный вид аномалии сериализации — это write skew («перекос записи»). Ситуация: две транзакции читают пересекающиеся наборы данных, и каждая на основе прочитанного изменяет данные, которые читала другая.

Пример из жизни — «Защита от овердрафта»:

В банке есть правило: общая сумма на всех счетах клиента не может быть отрицательной. Клиент Кевин имеет два счёта: saving ($500) и `checking` ($500). Итого — $1000. Он одновременно (в двух параллельных сессиях) пытается снять по $900 с каждого счёта.

```sql
-- Сессия A (снятие с saving)                      -- Сессия B (снятие с checking)
BEGIN; -- Repeatable Read                             BEGIN; -- Repeatable Read

-- Шаг 1: Обе транзакции читают ВСЕ счета Кевина
SELECT type, balance FROM account WHERE name = 'kevin';
-- saving: $500, checking: $500                    -- saving: $500, checking: $500
-- Обе видят: итого $1000. Снять $900 — можно.

-- Шаг 2: Каждая транзакция обновляет СВОЙ счёт
UPDATE account SET balance = balance - 900
WHERE name = 'kevin' AND type = 'saving';
                                                   UPDATE account SET balance = balance - 900
                                                   WHERE name = 'kevin' AND type = 'checking';

COMMIT; -- Успешно. saving = -$400                 COMMIT; -- Успешно. checking = -$400

-- Итог: saving = -$400, checking = -$400. Общая сумма = -$800.
-- Правило банка НАРУШЕНО, хотя ни одна транзакция не сделала ничего «нелегального».
```

Почему это аномалия сериализации? Если бы транзакции выполнялись последовательно, вторая увидела бы, что после первого снятия осталось всего $100, и **отказалась бы** от снятия $900. Но при параллельном выполнении обе увидели «старый» снимок с $1000, обе решили, что всё в порядке, и обе обновили разные строки — поэтому блокировки на запись не сработали.

Ключевой момент: транзакции обновили разные строки, но читали пересекающиеся данные. Именно из-за этого «пересечения» чтения и записи возникает аномалия, которую не видно на уровне отдельных строк.

#### Другой пример: «Взаимные вставки» (Intersecting Data)

Ещё один пример из документации PostgreSQL, который хорошо показывает суть аномалии:

```sql
-- Таблица: mytab (class, value)
-- Данные: (1, 10), (1, 20), (2, 100), (2, 200)

-- Сессия A                                         -- Сессия B
BEGIN; -- Serializable                              BEGIN; -- Serializable

-- A читает сумму по class = 1
SELECT SUM(value) FROM mytab WHERE class = 1;       -- 30
                                                    -- B читает сумму по class = 2
                                                    SELECT SUM(value) FROM mytab WHERE class = 2; -- 300

-- A вставляет строку в class = 2 (который читала B)
INSERT INTO mytab VALUES (2, 30);                   -- B вставляет строку в class = 1 (который читала A)
                                                    INSERT INTO mytab VALUES (1, 300);

COMMIT; -- Успешно                                  COMMIT; -- ОШИБКА: could not serialize access
```

Если бы A и B выполнялись последовательно, одна из них увидела бы вставку другой и её SUM был бы другим. Здесь каждая транзакция изменила данные, которые читала другая, и результат не соответствует никакому последовательному порядку.

#### Почему это возможно даже на Repeatable Read

Это важнейший практический момент. На уровне Repeatable Read в PostgreSQL:

Нет Dirty Read, Nonrepeatable Read и Phantom Read.

Но аномалия сериализации всё ещё возможна — в частности, в форме write skew.

Причина: Repeatable Read гарантирует, что каждая транзакция видит стабильный снимок. Но он не отслеживает зависимости между чтением и записью разных транзакций. Если A читает строки class=1, а пишет в class=2, а B наоборот — Repeatable Read не видит в этом проблемы, потому что каждая транзакция работает со своим снимком, и прямого конфликта «запись-запись» по одной и той же строке нет.

#### Как PostgreSQL защищает: SSI (Serializable Snapshot Isolation)

Начиная с версии 9.1, PostgreSQL использует SSI (Serializable Snapshot Isolation) — алгоритм, который отслеживает опасные структуры зависимостей между транзакциями (read-write dependencies) и, обнаружив потенциальную аномалию сериализации, откатывает одну из транзакций с ошибкой:

```
ERROR: could not serialize access due to read/write dependencies among transactions
HINT: The transaction might succeed if retried.
SQLSTATE: 40001 (serialization_failure)
```

Это называется «first committer wins»: та транзакция, которая попытается закоммититься второй и создаст опасную зависимость, будет отменена.

Важно: SSI не пытается «исправить» ситуацию или угадать вашу логику. Он честно говорит: «эта комбинация транзакций не может быть сериализована, повторите одну из них».

#### Практический сценарий: когда это реально кусается

1. Бизнес-правила, охватывающие несколько строк.
«Сумма заказов пользователя не должна превышать лимит». Две транзакции добавляют заказы разным строкам, но проверяют общую сумму. Каждая видит старую сумму, обе добавляют — лимит превышен.

2. Учёт ресурсов с «пересекающимися» проверками.
«Врач должен быть на смене, и его не должно быть на двух сменах одновременно». Две транзакции назначают одного врача на разные смены, каждая проверяет «нет ли его на другой смене», обе видят «нет» — и обе назначают.

3. Инвентарь с распределёнными остатками.
Товар хранится на двух складах. Правило: «суммарный остаток не может быть отрицательным». Две транзакции списывают товар с разных складов, обе проверяют общий остаток, обе видят достаточное количество — суммарный остаток уходит в минус.

4. Уникальность, проверяемая «вручную».
SELECT — «нет ли такого ключа?» → INSERT. На уровне Serializable PostgreSQL может обнаружить это как аномалию сериализации и выдать unique_violation (SQLSTATE 23505), который по сути является той же проблемой.

#### Как с этим бороться

Использовать уровень Serializable и обрабатывать ошибки сериализации. Это самый прямой путь. Транзакция может быть отменена с кодом 40001, и приложение должно повторить её целиком (с начала, включая всю логику принятия решений). PostgreSQL не делает автоматический retry, потому что не может гарантировать корректность — это ответственность приложения.

Явные блокировки (SELECT ... FOR UPDATE / FOR SHARE). Если вы можете определить, какие строки участвуют в проверке, заблокируйте их на чтение или запись, чтобы сериализовать доступ. Это грубее, но предсказуемее.

Материализация проверки в одной строке. Иногда можно свести «пересекающуюся» проверку к одной «агрегирующей» строке (например, хранить общую сумму в отдельной таблице и обновлять её атомарно), чтобы конфликт стал явным «запись-запись» и обрабатывался стандартными средствами.

#### Ключевая мысль

Аномалия сериализации — это не проблема одной транзакции или одной строки, а свойство группы транзакций: их совместный результат не соответствует ни одному последовательному выполнению. Она возможна даже на Repeatable Read (в форме write skew) и предотвращается на Serializable — но ценой появления ошибок 40001, которые приложение обязано обрабатывать и повторять. Задумываться о ней стоит всякий раз, когда бизнес-правило проверяет агрегат или набор строк, а транзакция изменяет часть этого набора (а не одну и ту же строку, которую все читают).

Мы разобрали все пять аномалий. Теперь у нас есть полный «список болезней». Следующий шаг — уровни изоляции как «лекарства»: начнём с Read Uncommitted (и сразу обсудим, почему в PostgreSQL он фактически превращается в Read Committed).

## Уровни изоляций транзакции

Уровень изоляции — это настройка (контракт) для транзакции, которая определяет, насколько сильно эта транзакция изолирована от эффектов других параллельных транзакций. Иными словами, это список гарантий: от каких аномалий данный уровень защищает, а какие допускает.

Это «лекарство», и, как у любого лекарства, у него есть побочные эффекты: чем строже изоляция (чем больше аномалий предотвращается), тем больше накладных расходов (блокировки, ошибки сериализации, падение параллелизма) и тем чаще приложению приходится повторять транзакции.

Ключевая мысль: уровень изоляции — это осознанный выбор компромисса между строгостью данных и производительностью/параллелизмом. «По умолчанию» — не значит «правильно для любой задачи».

### (ПЕРВЫЙ)

## Подробный разбор сочетаний аномалий и уровней изоляции транзакций

Аномалии — это то, от чего мы защищаемся. Это «болезни».

Уровни изоляции — это то, чем мы защищаемся. Это «лекарства» с разной силой действия и разными побочными эффектами.

Таблица «уровень × аномалия» — это, по сути, инструкция по применению: какое лекарство от какой болезни помогает. Именно поэтому мы сначала разбираем болезни по отдельности, а потом — лекарства.

### Разбор ячейки №1: Read Committed + Nonrepeatable Read

Это, пожалуй, самая важная для понимания ячейка, потому что Read Committed — это уровень изоляции по умолчанию в PostgreSQL, и в нём работает подавляющее большинство приложений.

#### Что это за аномалия?

Неповторяющееся чтение (Nonrepeatable Read) — это ситуация, когда в рамках одной и той же транзакции вы дважды читаете одну и ту же строку и получаете разные результаты. Это происходит потому, что между двумя вашими SELECT другая транзакция успела изменить эту строку и зафиксировать свои изменения (COMMIT).

#### Почему это возможно на Read Committed?

Секрет в том, как PostgreSQL работает на этом уровне. Каждая отдельная команда (например, каждый SELECT) внутри вашей транзакции видит снимок базы данных на момент своего собственного начала.

Представь, что твоя транзакция — это видеокамера, которая делает отдельный снимок (фотографию) базы данных перед выполнением каждой команды. Если между двумя твоими командами кто-то другой изменил данные и сохранил их, то на втором «снимке» ты увидишь уже новую версию данных.

#### Практический пример: «Почему мой отчёт сошёлся неверно?»

Это самый частый сценарий, с которым сталкиваются программисты.

Ситуация: Ты пишешь код для генерации финансового отчёта. Транзакция должна посчитать общую сумму на счетах, а затем — количество активных пользователей, чтобы рассчитать средний баланс.

```sql
BEGIN; -- Начинаем транзакцию с уровнем изоляции по умолчанию (Read Committed)

-- Шаг 1: Считаем общую сумму на всех счетах
SELECT SUM(balance) FROM accounts; 
-- Результат, например: 1 000 000

-- ... (в этот момент другая транзакция переводит 500 000 со счёта пользователя A на счёт пользователя B и делает COMMIT) ...

-- Шаг 2: Считаем количество активных пользователей
SELECT COUNT(*) FROM users WHERE is_active = true;
-- Результат, например: 100

COMMIT;
```

В чём проблема? Ты использовал два разных SELECT в одной транзакции. Второй SELECT увидел новый снимок данных, который уже включал изменения от параллельной транзакции. В итоге твои расчёты (сумма и количество) могут быть основаны на данных из разных «моментов времени», что приведёт к несогласованному (inconsistent) чтению. Отчёт будет внутренне противоречивым.

#### Как это исправить (практическая польза):

1) Использовать Repeatable Read: Если для отчёта критически важно видеть все данные «как один снимок», нужно явно установить более строгий уровень изоляции для этой транзакции. На уровне Repeatable Read снимок создаётся один раз при первой команде, и все последующие SELECT видят одни и те же данные, независимо от того, что делают другие транзакции.

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- ... теперь все SELECT видят один и тот же снимок ...
COMMIT;
```

2) Использовать SELECT ... FOR SHARE: Если тебе нужно не просто прочитать данные, но и гарантировать, что их не изменят до конца твоей транзакции, можно заблокировать нужные строки на чтение. Это не даст другим транзакциям их обновить.

```sql
SELECT * FROM accounts FOR SHARE;
```

#### Когда это НЕ проблема (и почему Read Committed — уровень по умолчанию)

Read Committed — уровень по умолчанию, потому что для большинства типовых веб-операций он идеален. Если ты просто читаешь данные пользователя для отображения на странице, или обновляешь одну запись, которая не участвует в сложных многошаговых вычислениях, то «неповторяющееся чтение» не принесёт вреда. Более строгие уровни изоляции требуют больше ресурсов и могут приводить к ошибкам, требующим повторных попыток.

Суть: Read Committed — это быстрый и эффективный уровень для простых операций. Но как только у тебя в одной транзакции появляется логическая зависимость между несколькими SELECT (как в примере с отчётом), ты должен задуматься о смене уровня изоляции на Repeatable Read.

Мы разобрали первую ячейку. Если этот формат понятен и полезен, давай следующим сообщением разберём следующую популярную и важную ячейку — Read Committed + «Потерянное обновление» (Lost Update). Это та самая аномалия, которая напрямую связана с гонками данных (race conditions) и которую PostgreSQL элегантно решает на уровне Repeatable Read.

### Разбор ячейки №2: Read Committed + «Потерянное обновление» (Lost Update)

Это, возможно, самая коварная и частая ошибка в приложениях, работающих с базами данных. Она напрямую связана с состоянием гонки (race condition) и может привести к незаметной потере данных.

#### Что это за аномалия?

Потерянное обновление происходит, когда две (или более) транзакции одновременно читают одну и ту же строку, а затем обе пытаются обновить её на основе прочитанных данных. В результате обновление, сделанное последней транзакцией, «затирает» изменения, сделанные предыдущей, и они теряются безвозвратно.

#### Почему это возможно на Read Committed?

На уровне Read Committed каждая команда видит свой снимок данных. Представь классический сценарий «прочитал — изменил — записал» (read-modify-write), который очень часто встречается в коде.

#### Практический пример: «Куда пропали деньги?»

Ситуация: У вас есть банковский счёт с балансом 1000. Два пользователя одновременно пытаются снять с него деньги: один — 200, другой — 300.

Код (псевдо-транзакция на уровне Read Committed):
```sql
-- Сессия A (Пользователь 1)                    -- Сессия B (Пользователь 2)
BEGIN;                                           BEGIN;

-- Шаг 1: Оба читают текущий баланс (1000)
SELECT balance FROM accounts WHERE id = 1; 
-- Результат: 1000                               -- Результат: 1000

-- Шаг 2: Каждая сессия вычисляет новый баланс у себя в приложении
-- (1000 - 200 = 800)                            -- (1000 - 300 = 700)

-- Шаг 3: Оба пытаются записать свой результат
UPDATE accounts SET balance = 800 WHERE id = 1; 
                                                 -- Сессия B ждёт, пока Сессия A завершит UPDATE

COMMIT; -- Сессия A фиксирует изменение (баланс стал 800)

                                                 -- Теперь UPDATE от Сессии B выполняется и записывает 700
                                                 COMMIT;

-- Итоговый баланс в базе: 700.
-- Ожидаемый баланс: 1000 - 200 - 300 = 500.
-- **Обновление от Сессии A (списание 200) ПОТЕРЯНО!**
```

Итоговый баланс — 700, хотя должен был быть 500. Деньги, которые «снял» первый пользователь, просто исчезли. Это и есть «потерянное обновление».

#### Когда это НЕ проблема (и почему Read Committed — уровень по умолчанию)

Важно понимать: Read Committed не предотвращает потерянные обновления, если в коде используется паттерн «прочитал-вычислил-записал». Однако это не значит, что уровень изоляции плохой. Проблема кроется в логике приложения.

Многие операции не являются «слепыми» перезаписями. Если вы используете атомарные SQL-команды, например, UPDATE accounts SET balance = balance - 200 WHERE id = 1;, то база данных сама заблокирует строку на время выполнения команды, и «потерянного обновления» не произойдёт. Проблема возникает именно тогда, когда логика чтения и записи разделена во времени (в коде или между несколькими запросами).

#### Как с этим бороться (практическая польза)

Существует несколько способов решения, и выбор зависит от вашей задачи.

1) Использовать пессимистичную блокировку (SELECT ... FOR UPDATE): Это самый надёжный способ. Вы явно говорите базе данных: «Заблокируй эту строку, я собираюсь её изменить». Другая транзакция не сможет прочитать эту строку для обновления, пока вы не завершите свою.
```sql
BEGIN;
-- Блокируем строку на время транзакции
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE; 
-- ... теперь можно безопасно вычислить новый баланс в приложении ...
UPDATE accounts SET balance = 800 WHERE id = 1;
COMMIT;
```

Это простое и эффективное решение, но оно может снижать параллелизм, так как заставляет другие транзакции ждать.

2) Использовать оптимистичную блокировку (проверка версии): Этот подход не блокирует строки, а проверяет, не изменились ли данные с момента их чтения. Для этого в таблицу добавляется колонка version.
```sql
-- Шаг 1: Читаем данные и версию
SELECT balance, version FROM accounts WHERE id = 1; -- balance=1000, version=1

-- Шаг 2: Обновляем, только если версия не изменилась
UPDATE accounts 
SET balance = 800, version = version + 1 
WHERE id = 1 AND version = 1; 

-- Если количество обновлённых строк = 0, значит, кто-то другой уже изменил данные. 
-- Приложение должно обработать эту ситуацию (например, перечитать данные и повторить попытку).
```

Этот метод хорош для систем с высокой конкуренцией, где блокировки нежелательны.

3) Повысить уровень изоляции до Repeatable Read: В PostgreSQL этот уровень автоматически предотвращает потерянные обновления. Если транзакция попытается обновить строку, которая была изменена и зафиксирована другой транзакцией после начала вашей, PostgreSQL выдаст ошибку could not serialize access due to concurrent update. Ваше приложение должно быть готово перехватить эту ошибку и повторить транзакцию.

#### Когда это НЕ проблема (и почему Read Committed — уровень по умолчанию)

Для многих веб-приложений, где пользователи редактируют разные записи (свой профиль, свой заказ), или где используются атомарные UPDATE, уровень Read Committed полностью достаточен и обеспечивает максимальную производительность. Проблема «потерянного обновления» — это сигнал о том, что в коде есть конкурентный доступ к одной и той же строке с паттерном «прочитал-изменил-записал», и именно этот участок кода нужно защитить одним из описанных способов.

Мы разобрали вторую, очень важную ячейку. Если готов, следующим шагом можем посмотреть на уровень Repeatable Read и его взаимодействие с другими аномалиями, например, с Phantom Read (который в PostgreSQL, в отличие от стандарта, на этом уровне уже невозможен).
